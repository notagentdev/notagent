# The Undo Tool, Ported From notagent-main-rust

## Objective

Give the agent a way to put a file back the way it was: an `undo` tool that reverts the most recent write, patch or delete on one named path. Today there is none — a bad edit is only undone by the model reconstructing the old content from memory, which is exactly the situation where its memory is least reliable.

The mechanism is a snapshot taken *before* every mutation. Three call sites in `../notagent-main-rust` do this and nothing else does: `fs_write.rs:139` (only when the file already exists — a new file has no prior state), `fs_patch.rs:522` (always) and `fs_remove.rs:61` (always). Each writes a copy of the current bytes into a per-file directory. `undo` restores the newest copy and deletes it, so repeated calls walk backwards through the history one step at a time.

Two properties of the reference design are worth stating because they are what make it simple enough to trust.

The store needs no index. A snapshot lands at `<base>/<fnv64(path)>/<timestamp>.snap` (`snapshot.rs:88` and `:95`), where the timestamp is formatted `%Y-%m-%d_%H-%M-%S-%9f` — zero-padded to nanoseconds, so lexical order *is* chronological order. Finding the newest snapshot is `max()` over the directory listing (`service.rs:39`), with no metadata to keep in step with the files.

Undo is not a permission decision. The reference lists `ToolCatalog::Undo(_)` among the tools that skip permission checks (`catalog.rs:1500`), and the reasoning holds: the only state undo can produce is a state the user already had, and it can only reach paths this agent itself wrote. Asking permission to take back a change is asking permission for the remedy rather than the damage.

Assumptions where the request was open:

- The tool is named `undo` and takes a single `path`, matching the reference's `FSUndo { path: String }` (`catalog.rs:719`). Not `fs_undo` — our registry has no `fs_` prefixes.
- Snapshots live under `get_agent_dir()/snapshots`, mirroring the reference's `base_path.join("snapshots")` (`env.rs:111`). That is `~/.notagent-v2/agent/snapshots` here, outside the repository, so a snapshot is never itself a file the agent might commit.
- `undo` joins the worker shell, not the read-only one. It writes to the workspace; that a read-only session cannot undo anything follows from its not having changed anything.
- Snapshots are taken by `write`, `edit` and the two minified patch tools. We have no delete tool — deletion goes through `bash`, which cannot be snapshotted without inspecting arbitrary shell commands, so a file removed by `rm` stays removed. The tool's description has to say so rather than let the model discover it.

## Implementation Plan

- [ ] 1. Add the snapshot store as its own module under `crates/notagent/src/core/`, holding the four operations the reference splits across `notagent_snaps::SnapshotService` and `notagent_domain::Snapshot`: derive a file's snapshot directory, write a snapshot of its current bytes, find the newest snapshot in that directory, and restore-and-consume it. Keep the reference's layout exactly — an FNV-64 hash of the canonicalised path as the directory name, and a `%Y-%m-%d_%H-%M-%S-%9f.snap` file name whose lexical order is its chronological order. The format is what makes the store indexless, so it is a compatibility surface rather than an implementation detail.

- [ ] 2. Canonicalise the path the way `Snapshot::create` does (`snapshot.rs:65`): resolve it when the file exists, fall back to the path as given when it does not, and refuse a relative path outright. A file and the same file reached through a symlink must hash to one directory, or undoing through the other name would find nothing — and a snapshot taken before a delete has to hash the same after it, when canonicalisation can no longer resolve.

- [ ] 3. Take a snapshot before each mutation, at the same three moments the reference does. `write` (`crates/notagent/src/core/tools/write.rs`) snapshots only when the file already exists. `edit` (`tools/edit.rs`) and both minified patch tools (`tools/patch_minified.rs`) always snapshot, since they only ever act on a file that is already there. Place the call before the lease is committed, matching the reference's ordering: a snapshot that was written but whose mutation then failed costs one stale file, while a mutation whose snapshot failed costs the ability to undo it.

- [ ] 4. Decide what a failed snapshot does to the mutation it precedes. The reference propagates the error with `?`, so a snapshot failure fails the write. Follow it, but check the one case where that is wrong: a workspace on a read-only or full filesystem would become unwritable through us while `bash` could still write it. If that trade looks wrong in testing, degrade to writing anyway and reporting that the change cannot be undone — never silently.

- [ ] 5. Add the `undo` tool itself as `crates/notagent/src/core/tools/undo.rs`, following the shape of the tools around it: a `ToolDefinition` with a `path` parameter, a pluggable operations trait for tests, and the same validation the reference performs before touching anything — absolute path, and not a sensitive file (`fs_undo.rs:29`). Read the content before and after restoring, since the output is built from that pair.

- [ ] 6. Report the outcome as the four states the reference distinguishes (`operation.rs:662`), because they are four genuinely different things and a single "done" would hide which happened: neither before nor after means there was nothing to undo; no before but an after means the file was restored after having been deleted; a before with no after cannot occur through our tools but is kept for symmetry; both means the content was rolled back, and the output carries the diff between them. Match the reference's element names and attributes — `file_undo` with `path`, `status`, `total_lines` — so a transcript from either implementation reads the same.

- [ ] 7. Register the tool: `ToolName::Undo` in `core/tools.rs` with its `as_str`, its entry in `ALL_TOOL_NAMES`, its factory arms, and its options struct. Add it to `WORKER_ADDITIONAL_TOOLS` in `core/modes/shells.rs`, which puts it in `MUTATING_TOOLS` automatically — correct, since it writes.

- [ ] 8. Let `undo` through the permission chain without asking, as the reference does. The cleanest place is a policy in the existing chain rather than a special case at the call site; `default-tool-approve` (`core/permissions/policies.rs:147`) already approves a fixed set by name and is where a reader would look. State the reasoning in the code: undo can only produce a state the user already had, on a path this agent already wrote.

- [ ] 9. Render the call as the reference does — the tool name and the path, nothing else (`tool_renderers.rs:2342`) — and leave the result unrendered. The user watches the file change in their editor; a diff in the transcript would repeat what the original tool call already showed, in reverse.

- [ ] 10. Write the tool description. It has to say two things the model cannot infer: that undo steps back one mutation per call and can be repeated to walk further back, and that files removed with `rm` through `bash` are not recoverable, since nothing snapshotted them. The reference's description (`descriptions/fs_undo.md`) says neither, and both are how the tool is misused.

- [ ] 11. Cover the store with the reference's own cases, which are the ones that matter (`service.rs:136-252`): restoring modified content, an error when no snapshot exists, restoring a file that was deleted after its snapshot, taking several snapshots and getting back the most recent, and undoing twice to walk back two steps. Add one the reference lacks: two files whose paths hash into different directories do not interfere.

- [ ] 12. Cover the tool end to end: each of the four output states, a relative path refused, a sensitive path refused, and the round trip that is the whole point — write a file, change it, undo, and get the first content back.

- [ ] 13. Decide what bounds the store's growth, and write down what was decided. The reference has no answer: every mutation of every file leaves a snapshot forever, so a long session over a large repository accumulates a copy per edit. A per-directory cap (keep the newest N) or an age cutoff are both cheap given that the file names sort chronologically. Whichever is chosen, the tool must not silently lose the step a user is about to undo — prefer a generous cap over a short one.

## Verification Criteria

- Writing a file, changing it, then calling `undo` restores the first content exactly, including its line endings.
- Calling `undo` twice walks back two mutations; calling it once more than there are snapshots reports that there is nothing left to undo rather than failing obscurely.
- A file deleted after its snapshot is recreated by `undo` with its snapshot content.
- Creating a file with `write` leaves no snapshot; undoing it reports that there was nothing to undo, rather than truncating the file to empty.
- Two files with the same base name in different directories undo independently.
- `undo` never prompts for approval, in `manual` mode included.
- A read-only session does not have the tool at all.
- Snapshots land under `~/.notagent-v2/agent/snapshots` and never inside the workspace, checked by asserting the path rather than by inspection.
- `cargo clippy -p notagent --lib --tests` is clean, and no new `unwrap()`/`expect()` sits on a path that a missing directory, an unreadable snapshot or a non-UTF-8 file can reach.

## Potential Risks and Mitigations

1. **A snapshot is a full copy, taken on every mutation.** An agent that rewrites a large file in a loop writes that file to disk twice per iteration, and the store grows without bound (task 13).
   Mitigation: cap per directory and skip the snapshot when the newest one is byte-identical to the current content — a re-run that changes nothing then costs nothing. Measure with a large file before choosing the cap.

2. **Non-UTF-8 files.** The reference reads with `read_utf8` (`fs_undo.rs:31`) and would fail on a binary file, but it snapshots with a byte read and byte write, so the snapshot itself is sound.
   Mitigation: keep the store on bytes throughout and let only the *reporting* require UTF-8 — a binary file can then still be restored, with an output that says so instead of the diff.

3. **The snapshot directory is derived from a hash, so a path collision silently mixes two files' histories.** FNV-64 over full paths makes this vanishingly unlikely, but the failure is silent and destructive if it happens.
   Mitigation: write the original path into the snapshot directory as a plain marker file and verify it before restoring. Cheap, and it turns a silent wrong-file restore into a clear error.

4. **A file the user edited by hand between the snapshot and the undo.** Undo overwrites their work with the older content and there is nothing to warn them.
   Mitigation: the output already carries the diff between what was there and what was restored, which is the record they need. Do not add a confirmation prompt — see task 8 — but make sure the diff is in the output rather than only the restored content.

5. **The reference's `undo` is not in a lease.** Our mutating tools take a file lease to serialise concurrent writers; an undo that bypasses that can race a subagent's write on the same path.
   Mitigation: take the same lease `write` takes, for the same duration. This is a deliberate deviation from the reference, which has no leases at that call site.

## Alternative Approaches

1. **Snapshot into git rather than a private store.** A `git stash`-like commit per mutation would give history, diffing and cleanup for free. Rejected: it needs a repository, it fights the user for the index, and it cannot snapshot files that are ignored or outside the worktree — all cases where undo is most wanted.

2. **Keep the previous content in memory rather than on disk.** Simpler and faster, with no store to bound. Rejected because the value of undo is highest exactly when the process did not survive — after a crash, or in a later session looking at a file that was mangled an hour ago.

3. **One undo history per session rather than per file.** Reverting the whole last operation, whatever file it touched, is closer to what "undo" means in an editor. Worth considering later, but it needs an ordered log across files, which is the index the current design deliberately does without. The per-file form composes into it later; the reverse is not true.

4. **Ship a `remove` tool alongside it**, as the reference does (`fs_remove.rs`), so that deletions are snapshotted too and `undo` has no hole. Considered and rejected (user decision 2026-08-20): `remove` takes a single file path, so the deletion it makes undoable is the cheap one, while the expensive `rm -rf <directory>` still goes through `bash` — where `destructive_command_ask` (`core/permissions/policies.rs:238`) already stops it every time and refuses to remember the answer. The cost is permanent: one more tool in every system prompt and one more decision the model gets wrong whenever `rm` is the phrase it reaches for first. Revisit if deletions turn out to be a real source of damage; the snapshot store is the expensive half and it exists either way, so `remove` would be a small file plus its registration.

5. **Snapshot inside `write`/`edit`'s operations trait rather than at the call site.** Fewer touch points, and a new mutating tool would get snapshots automatically. Rejected because the trait is the seam tests replace: a fake operations impl would then silently stop snapshotting, which is the one behaviour these tests exist to check.
